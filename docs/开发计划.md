# Henfon 商城完整开发任务与周期评估

> 评估日期：2026-08-29
>
> 适用范围：`shop-admin` 后端、`shop-web` 管理端、`shop-portal` 商城门户端
>
> 当前架构：Java 21 + Spring Boot 3.4.5 的单体多模块后端；React + Vite 双前端；MySQL 8、Redis、MinIO、RocketMQ

## 1. 结论摘要

项目当前处于“可运行原型 + 后端基础能力 + 首批门户接口联调”阶段，还没有达到可直接上线的完整商城标准。

当前最重要的判断如下：

- 后端继续采用单体多模块架构，暂不拆分微服务。模块边界已经按领域划分，后续通过领域服务接口、RocketMQ 事件和 Outbox 机制保持可演进性。
- `shop-web` 的页面和交互较完整，但目前真正接入后端的主要是管理员登录、动态菜单/RBAC 和商品目录；订单、会员、库存、营销、财务、报表等页面仍以本地演示数据或本地状态为主。
- `shop-portal` 已经接入商品、Banner、优惠券查询、购物车、收藏、地址和订单基础接口，但仍保留大量 fallback 数据；会员登录是预置演示用户，支付为模拟流程，订单详情商品明细、评价、对比历史等还未形成完整闭环。
- 生产可用版本的关键缺口集中在：会员认证、订单状态机、库存扣减、支付回调、售后退款、后台 CRUD、MinIO 文件上传、RocketMQ 可靠投递、测试和部署运维。

### 周期结论

以下周期以“推荐团队”估算：2 名后端、2 名前端（分别主负责 Web 和 Portal）、1 名测试兼产品、1 名兼职 DevOps。

| 目标 | 推荐周期 | 说明 |
| --- | ---: | --- |
| 可演示 MVP | 8-10 周 | 完成登录、商品浏览、购物车、下单模拟、后台商品和订单基础管理 |
| 可联调业务版本 | 12-15 周 | 增加真实会员、库存、营销、内容、物流和支付适配 |
| 生产候选版本（RC） | 18-22 周 | 完成安全、幂等、消息可靠性、测试、监控、部署和上线演练 |
| 单人全栈开发 | 24-32 周 | 不建议，测试、设计和运维会成为瓶颈 |

按当前代码基线，建议按 **18-22 周生产候选版本** 规划；如果暂时只做内部演示，可以先压缩到 8-10 周 MVP。

### 2.2 数据库现状

现有初始化脚本位于 `shop-admin/db/init`：

- `001_create_database.sql`：创建 `henfon-shop` 数据库。
- `002_identity_tables.sql`：系统用户、部门、角色、菜单、数据权限、登录/操作日志、会员表。
- `003_catalog_tables.sql`：类目、商品、SKU、商品媒体。
- `004_trade_tables.sql`：订单、订单明细、购物车、售后。
- `005_portal_tables.sql`：商品卖点/参数、Banner、评价、会员地址/收藏/对比、优惠券、会员优惠券、物流轨迹。
- `006_inventory_tables.sql`：仓库、库存台账、库存锁定和库存流水。
- `007_trade_idempotency.sql`：订单幂等键字段及会员维度唯一索引。
- `008_member_address_default.sql`：会员未删除默认地址唯一约束。
- `009_trade_event_outbox.sql`：交易订单领域事件 Outbox 表及重试索引。
- `010_trade_after_sale_indexes.sql`：售后处理中目标唯一约束和会员查询索引。
- `011_payment_order_tables.sql`：支付单及支付回调幂等字段。
- `012_payment_refund_tables.sql`：退款单、退款回调和退款幂等字段。
- `013_marketing_coupon_usage.sql`：优惠券核销/回滚流水及唯一索引。
- `014_content_review_reply.sql`：评价商家回复字段，采用幂等迁移脚本。
- `015_member_tags_consumption.sql`：会员标签、会员标签关联和消费统计表，并回填历史已支付订单。
- `016_table_comments.sql`：补齐历史表的表级注释元数据。
- `018_payment_invoice_tables.sql`：订单发票申请、状态和开票结果表。
- `019_inventory_stocktake_tables.sql`：库存盘点单及盘点明细表。
- `020_content_notification_tables.sql`：会员站内通知及事件幂等索引。
- `021_inventory_supplier_tables.sql`：库存供应商基础信息、状态和逻辑删除表。

命名规范已经形成：系统模块使用 `sys_`，商品使用 `catalog_`，交易使用 `trade_`，会员使用 `member_`，营销使用 `marketing_`，内容使用 `content_`。后续新增表必须继续遵循该规范，并补充索引、唯一约束、逻辑删除和乐观锁字段。

当前数据库结构能支撑第一阶段联调，但正式上线前还需要补充：操作审计扩展、售后凭证和发票信息等表；支付单、退款单、优惠券核销流水、评价回复字段、订单 Outbox 与库存锁定流水已完成。

门户当前采用“后端优先、失败回退演示数据”的策略，适合开发预览，不适合生产环境。上线前必须增加明确的错误态、重试、登录拦截和数据一致性处理，并逐步移除 fallback。

## 4. 依赖关系与推荐实施顺序

核心依赖链如下：

```text
接口/状态定义
    ├── 管理员与会员认证、权限
    ├── 商品/类目/SKU/媒体
    │       └── 库存与价格校验
    ├── 购物车
    │       └── 订单创建
    │               ├── 营销优惠券计算
    │               ├── 库存预占/扣减
    │               └── 支付与退款
    │                       └── 发货/物流/售后
    └── 领域事件与报表
```

推荐顺序：

1. 先完成 API 契约、会员认证、订单和库存状态定义。
2. 再完成商品/SKU/媒体和门户商品浏览，保证商品事实数据来源统一。
3. 接着完成购物车、订单、库存和支付主链路。
4. 在主链路稳定后接入营销、售后、物流、报表和通知。
5. 最后集中处理性能、安全、监控、测试和生产部署。

不要先花大量时间拆分微服务或重做页面视觉；当前主要风险是业务一致性和接口闭环，不是模块数量或 UI 数量。

## 7. 风险、决策和非功能要求

### 需要尽快确认的业务决策

- 会员登录是手机号验证码、账号密码，还是两者并存。
- 支付渠道和结算主体；是否需要微信/支付宝双渠道。
- 物流服务商和物流轨迹查询方式。
- 库存是单仓还是多仓，是否允许超卖，锁库存时机是什么。
- 优惠券是否允许叠加，退款后是否恢复，秒杀是否独立库存。
- 售后时效、退货地址、质检和退款节点。
- 发票类型、抬头、税号和开票平台。
- 是否需要多租户；当前表结构保留了 `tenant_id`，但业务尚未全面启用。

### 必须满足的非功能指标

- 管理端接口默认需要管理员 JWT；门户会员接口使用会员 JWT，不信任 URL 中的 `memberId`。
- 所有金额使用 `DECIMAL` 和后端重算，前端金额只作为展示。
- 创建订单、支付回调、退款回调、库存扣减和优惠券领取必须幂等。
- 关键操作必须记录操作人、请求链路、前后值和业务单号。
- 商品媒体、评价图片、售后凭证统一走 MinIO，不允许把大文件存入 MySQL。
- 跨模块最终一致性通过 RocketMQ 事件实现，并具备重试、死信和人工补偿能力。
- 生产环境禁止使用当前默认密码、默认 JWT 密钥和公开 MinIO 账号。

## 8. Definition of Done（完成标准）

一项功能只有同时满足以下条件，才标记为完成：

- 数据库表、索引、迁移脚本和初始化数据已提交。
- 后端接口、参数校验、权限校验、错误码和方法注释齐全。
- `shop-web` 和/或 `shop-portal` 已接入真实接口，不依赖生产 fallback。
- 成功、失败、空数据、重复提交、权限不足和网络异常均有处理。
- 单元测试/集成测试/关键流程测试已通过。
- 日志、审计、监控和告警已覆盖关键路径。
- README 或部署文档已更新，其他开发者可以在干净环境复现。
- 产品验收通过，数据库和消息补偿方案已经演练。

## 9. 下一步建议（当前迭代）

建议下一轮先做以下 P0 任务，不要同时铺开所有页面：

1. 定义会员 JWT 和订单状态机，去掉门户接口对 `memberId` 的信任。
2. 在已有后台发货、取消、备注、退款基础接口上，补齐订单状态机、售后单、退款单和库存接口。
3. 完成会员后台查询/冻结，并将地址接口迁移到会员 JWT 上下文。
4. 完成商品 SKU、媒体上传和门户 SKU 价格/库存展示。
5. 将 `shop-web` 订单、会员、库存页面从 mock 状态改成真实接口驱动。
6. 将 `shop-portal` 订单详情商品明细、优惠券领取、对比历史和评价查询接入后端。
7. 为订单创建增加库存预占、幂等键和事务边界，再进入真实支付接入（库存预占、事务边界和幂等键已完成，价格/优惠券服务端重算待补齐）。

这 7 项完成后，项目会从“页面可演示”进入“核心业务可联调”阶段，后续再扩展营销、财务、报表和生产运维能力。
