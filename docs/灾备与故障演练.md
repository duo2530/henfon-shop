# 灾备与故障演练方案

## 备份策略

- MySQL：每日全量、每小时 Binlog 归档，保留 30 天；备份文件加密后保存到独立对象存储。
- Redis：开启 AOF，每日复制 RDB 快照；Redis 仅作为缓存和令牌存储，业务数据以 MySQL 为准。
- MinIO：每日增量同步对象及元数据，保留 30 天版本；禁止只备份数据库而遗漏媒体对象。
- RocketMQ：保留消息轨迹和死信队列，至少保留 14 天，消费失败通过 Outbox/补偿任务重放。

## 恢复流程

1. 冻结写入流量并记录故障时间点，避免恢复期间产生新的不一致数据。
2. 在隔离环境恢复最近一次 MySQL 全量备份，再按时间点回放 Binlog。
3. 恢复 MinIO 对象和 RocketMQ 消息后，启动上一版本应用进行数据校验。
4. 校验订单、库存锁定、支付回调和发票四类核心数据，再逐步放开流量。

## 故障演练

- MySQL 主库不可用：切换只读副本，验证订单查询、库存查询和后台登录。
- Redis 不可用：验证登录令牌失效、幂等查询和缓存重建，确认业务错误可观测。
- RocketMQ 堆积：暂停生产者，消费死信并核对 Outbox 状态，确认消息不重复执行。
- MinIO 不可用：验证商品媒体上传失败提示、已存在对象访问和重试策略。
- 应用版本回滚：切换上一镜像标签，执行健康检查和核心接口冒烟，数据库只允许向前兼容。

每次演练记录故障开始/恢复时间、影响范围、数据校验结果和改进项，形成可追踪的演练报告。
