# 秒杀功能优化方案

当前秒杀是「普通下单 + 一层活动库存校验」：请求体带可选 `flashSaleId` 才走秒杀分支，`trade_order` 没有秒杀字段，没有独立库存池，Redis/MQ 不参与扣减，防超卖靠 `marketing_flash_sale_item` 的条件更新（`sold_stock + qty <= total_stock`）+ InnoDB 行锁。相关表三张：`marketing_flash_sale`（活动）、`marketing_flash_sale_item`（明细，sku_id 可空）、`marketing_flash_sale_reservation`（预占流水）。

下文分三块：不改会持续出错的问题、性能与体验、标准版长什么样。行号对应 2026-09-17 的代码。六项已按此实施，落点见文末「实施记录」；标准版一节仍是设计说明，未动代码。

## 一、库存校验用错了基数

`validateAvailableStock`（MarketingFlashSaleService:925）拿 catalog 的 `catalog_sku.stock` / `catalog_product.current_stock` 当上限，这两个是总库存语义，下单流程不改它们。真实可用库存在 `inventory_stock.available_stock`（shop-inventory 维护），两模块之间没有同步代码 —— 实测 product 1 是 catalog 128 / inventory 可用 127（已售 1）。差距随销售扩大：总库存 1000、已售 500 的商品，活动库存可以合法配到 1000，门户显示剩 1000，实际卖到 500 就撞「库存不足」。

改三处：

1. `InventoryStockService` 加 `availableStock(Long skuId)` 和 `availableStockBySkuIds(Collection<Long>)`，口径与下单扣减一致：`defaultWarehouse()` + skuId。
2. shop-marketing/pom.xml 显式声明 shop-inventory —— 现在能编译是靠 shop-trade 传递依赖。
3. `MarketingFlashSaleService` 换口径：明细指定 SKU 取该 SKU 可用量；sku_id 为 NULL 的取商品下 status=1 全部 SKU 可用量之和（下单扣的是请求里那个具体 SKU，上限得按商品汇总）。构造器随之从 7 参增到 9 参（库存服务、门户缓存）。

```java
private int resolveAvailableStock(MarketingFlashSaleSaveRequest.Item item) {
    if (item.skuId() != null) {
        return inventoryStockService.availableStock(item.skuId());
    }
    return sumAvailableStockByProduct(item.productId());
}
```

保存和启用两处都校验。保存是覆盖式重写明细，放行会让运营以为配好了；启用时按最新可用量复校，保证不会静默上线。零存量超配，所以不会出现「改个活动名字被库存卡住」。

存量数据不用清。全库 5 条明细按「剩余量 > 可用量」核对零条超配；判据要用 `total_stock - sold_stock`，用 `total_stock > available` 会把「配 128、已售 1」的正常明细误报成超配。

`MarketingFlashSaleServiceTest`（:38-45）是手搓 mock，要补一个 InventoryStockService。`validate()`（:883-940）每条明细查一次库存，和它已有的 product/sku 查询一样是 N+1，明细个位数，先不动。验证：`mvn -o -pl shop-inventory,shop-marketing -am test`；再手工把某条明细配到大于可用量，保存应返回 `MARKETING_FLASH_SALE_STOCK_INVALID` 且文案带可用量。

## 二、启用活动时复校一次

`updateStatus`（:847-856）只改状态不校验。保存到启用之间隔多久都可能，期间普通订单会把库存买走，而启用是对外承诺库存的时刻。

```java
if (Integer.valueOf(1).equals(status)) {
    validateActivityAvailableStock(id);
}
```

遍历活动全部明细，跳过剩余量已 <= 0 的，余下比剩余量和可用量。启用从「必定成功」变成「可能失败」，前端 toggleStatus（FlashSaleManagementView.tsx:381-386）已有 try/catch，不用改。`zeroIfNull(Integer)` 需要重载，别改坏现有 Long 签名。

## 三、售后退货不回补活动名额

`FlashSaleReservationService.release` 的调用点只有三个：后台取消（TradeOrderService:527）、买家取消（:551）、超时关单（:976）。支付成功不处理，所以已支付订单的预占流水仍是 status=0。

售后退货（TradeAfterSaleService.confirmReturn:230）回补了普通库存却不碰活动名额，货退回仓库、`sold_stock` 不减，名额永久消失。先分清：退款不回补是全局口径（退款 ≠ 退货），全项目唯一回补入口就是 confirmReturn，不一致的只有售后退货这一侧。

改法：TradeAfterSaleService 注入 `ObjectProvider<FlashSaleReservationService>`（照抄 TradeOrderService:77，避免循环依赖），回补库存之后加一次：

```java
reservationService.release(afterSale.getOrderId());
```

release 只处理 status=0 的流水、处理完置 1，重复调用安全。整单释放够用：退货粒度本身就是整条订单明细，不支持部分数量退货，秒杀单恒为单明细单件。实现时留一句注释说明这个约束。

验证要造一笔已支付秒杀订单再走退货确认，会产生真实数据。

## 四、status=2 一码两义

`warmupUpcomingActivities`（:252-260）把自然过期的启用活动写成 2，人工停用也是 2，`activityStatusText`（:688）见 2 一律「已停用」。列表页筛选下拉只有草稿/已启用/已停用（FlashSaleManagementView.tsx:414），选「已停用」会把自然过期的一起捞出来，运营以为是自己关的。

最小改法：时间判断提到 status==2 之前。后端 `statusText`（:109-118）与 activityStatusText 是逻辑相同的两份实现，一起改。

```java
if (activity.getEndAt() != null && now.isAfter(activity.getEndAt())) {
    return "已结束";
}
if (status == 2) {
    return "已停用";
}
```

遗留：列表筛选项没动，选「已停用」仍会捞到自然过期的。彻底改法是调度器不再改业务状态，过期活动保持 status=1，靠 start_at/end_at 过滤，status 变成纯人工意图字段；代价是「已启用」筛选要改成「启用且未结束」或新增「已结束」，改面扩散，不抵。

## 五、混合结算丢活动价

`CheckoutModal.tsx:329` 只在 `items.length === 1` 时带 flashSaleId，多件结算时变成 undefined，服务端 `validateCatalogItems`（TradeOrderService:1059）回到严格价格校验，抛 `TRADE_PRICE_CHANGED`「商品价格已变化，请刷新后重试」—— 原因和文案对不上。补字段也解决不了：reserve 要求订单内所有商品都在活动里，混合结算带上 flashSaleId 会被 `MARKETING_FLASH_SALE_ITEM_INVALID` 拒掉。

所以前端禁止混入：`handleFlashSaleBuy`（App.tsx:1263）与商品「立即购买」都只把单件临时结算项塞进结算，购物车结算（App.tsx:1657）取勾选项、而购物车项从不带 flashSaleId —— 混合场景目前实际不可达。因此在提交订单前加一道断言（`CheckoutModal.handlePayOrder`）：结算项里出现秒杀商品且不止一件时直接提示「秒杀商品需要单独结算」，不再把订单级 flashSaleId 静默丢掉。服务端配套改文案：`TRADE_PRICE_CHANGED` 补一句「秒杀商品需单独结算」，`MARKETING_FLASH_SALE_ITEM_INVALID` 带上具体商品 ID。

把 flashSaleId 从订单级下沉到明细级要给 `trade_order_item` 加列（新增编号脚本 + manifest 哈希变更，按约定需确认）。除非确定要支持一次结算多件秒杀商品，不划算。

## 六、门户列表缓存与限流

`activeFlashSales()` 每请求查 4 张表，再对每个商品调一次 `resolveAccessUrl()`（HMAC-SHA256）。门户 App.tsx:383 每 30 秒全量轮询，接口在 SecurityConfiguration:58 是 permitAll，外部可以零成本刷。实测（本机 dev）30 并发 670 req/s、120 并发 675 req/s —— 吞吐不动、延迟等比放大，已饱和；不查库的对照路径 1535 req/s。

缓存先做。shop-marketing 经 shop-identity 已有 StringRedisTemplate，缓存封装在 `FlashSalePortalCache`：key `shop:marketing:flash-sale:portal`，TTL 10 秒，JSON 序列化，读写两处都在 Redis 异常时降级为直连数据库。`activeFlashSales()` 先读缓存，未命中再走原查询并回写 —— 原查询逻辑抽成私有 `loadActiveFlashSales()`。不做主动过期之外的失效：reserve/release 太频繁，每次删缓存等于没缓存；只有 save/updateStatus/delete 三处配置变更调 `evict()`，让调整立即生效。缓存里含预签名图片地址，要确认签名有效期远大于 10 秒。

限流：`PortalFlashSaleRateLimitFilter`（shop-marketing/config）只对 `/api/portal/marketing/flash-sales*` 与 `POST /api/portal/trade/orders` 计数，照抄 LoginFailureTracker 的 increment + expire，维度取客户端 IP（优先 X-Forwarded-For），读写分开配额。开关与阈值走 `shop.marketing.flash-sale-rate-limit-*` 三个配置项（dev 默认关，prod 默认开 300 次/分钟），超限返回 429 `PORTAL_RATE_LIMITED`，Redis 异常放行。针对的是「秒杀洪峰拖垮主站」：抢购、普通下单、管理端、健康检查共用同一个 Tomcat 线程池和 Hikari 连接池（dev 20 / prod 50），没有业务隔离。

## 标准版秒杀

这不是现在的实施项，是「真要做时做成什么样」。与当前实现的差别只在两处：库存判定前置到 Redis，下单从同步落库变成异步排队。其余（活动配置、明细、预占流水、对账口径）都是通的，不用重做。

现状离标准版比想象的近：`warmupUpcomingActivities()` 的扫描窗口（start_at ∈ (now, now+30min)，参数 `shop.marketing.flash-sale-warmup-minutes:30`，每 60 秒一轮）就是预热该有的窗口，它也确实写库（把 sold_stock 为 null 的明细补成 0）。缺的只是最后一步：把数据搬进内存。

### 库存预热

**装载** —— 只装「每个明细还剩几个名额」这一个数，活动元数据不装（点查一次活动表不是瓶颈，装进来只是多一份要维护一致性的副本）。挂在 warmupUpcomingActivities 的 valid 分支（:292）：

```java
Duration ttl = Duration.between(now, activity.getEndAt()).plusHours(1);
for (MarketingFlashSaleItem item : items) {
    redisTemplate.opsForValue().set("shop:marketing:flash-sale:quota:" + item.getId(),
            String.valueOf(item.getTotalStock() - zeroIfNull(item.getSoldStock())), ttl);
}
```

用 set 不用 increment：预热每 60 秒扫一轮，窗口内的活动会被反复扫到，累加式写法会把名额越加越多，覆盖写天然幂等。只装未开始的活动 —— 已经开跑的如果被覆盖写，会冲掉用户刚扣掉的名额，现有查询条件 `.gt(startAt, now)` 正好保证这点，别改。

**准入** —— 一条 Lua 原子完成「查余量 → 扣减」，写法照 MemberTokenStore:33 的 DefaultRedisScript，脚本里不出现网络调用：

```
local quota = redis.call('get', KEYS[1])
if not quota then return -2 end
if tonumber(quota) < tonumber(ARGV[1]) then return 0 end
redis.call('decrby', KEYS[1], ARGV[1])
return 1
```

返回 1 成功、0 售罄、-2 未预热。-2 不当错误处理，放行到 MySQL 老路，那种情况下老路是唯一正确的路径。

限购计数不一起搬。现状那次 `reservationMapper.selectList().sum()` 是读操作，瓶颈不在它，在 `matchActivityItem` 的 FOR UPDATE 写锁窗口；搬进 Redis 省不下多少，却要求取消、退款、超时关单三条释放路径都同步减计数，一致性面反而变大。

**落库** —— MySQL 那段一行不改，`sold_stock + qty <= total_stock` 的条件更新继续留着。它是「Redis 挂了、或 Redis 与本库漂移了也不会超卖」的唯一保证。Redis 在链路里只是准入闸门，账本始终是 MySQL。

**补偿** —— 预减成功但落库失败要分两种处理：

| 失败 | 处理 |
|---|---|
| 条件更新影响 0 行（真售罄） | 不还。MySQL 说售罄就是售罄，Redis 多放了该被纠正，还回去只会让它继续多放 |
| 其他异常（DB 断连、库存服务异常、事务回滚） | 还回去，否则名额永久漏掉 |

异常要继续 `throw`，`@Transactional` 靠异常触发回滚，吞掉等于不回滚。`release(Long orderId)`（:216）补一次 INCRBY —— 取消、超时关单、售后退货三条路径都走这个方法，一处改完全覆盖。

**对账** —— 漂移只有一处来源：预减成功但订单最终没落库、又没走 release（比如进程崩在中间）。所以不需要高频对账，活动进行中不做覆盖写，只在检测到「MySQL 已售罄而 Redis 仍有余量」时修正一次并告警。活动结束后不显式删 key，靠 TTL 兜底。

**降级** —— 准入段整段 try/catch 包住，任何异常（连不上、超时、脚本报错）都放行到 MySQL 老路。这是 fail-open，安全性由条件更新保证，代价只是退回现状的吞吐。开关仿 `shop.rocketmq.consumer-enabled` 加 `shop.marketing.flash-sale-preheat-enabled`，默认 false。

**收益边界** —— 省下来的是锁窗口，不是数据库查询。现状每个请求都要进 `matchActivityItem` 拿 FOR UPDATE 并持锁到事务提交；预热后没抢到的连 `activityMapper.selectById` 都不做。所以提升幅度等于被拦掉的比例：库存 100、一万人抢，99% 止步内存；库存量和并发都在几百这个量级时，拦掉的比例不高，绝对收益有限。

### 异步下单

把「同步落库」换成「入队 + 消费者落库」：Redis 扣减通过、入队成功即返回「已受理」，前端轮询结果，请求耗时不再包含一整笔下单事务。代价是三种新的中间态 —— 入队失败要当场回补名额、消费者落库失败要重试或回补、用户取消要处理「已受理未落库」。项目里基础已有（RocketMQ 21 个 topic + `trade_event_outbox` 每 5 秒扫表），但 dev 下 `SHOP_ROCKETMQ_CONSUMER_ENABLED=false`，consumer bean 被摘掉，本地跑不通这条链路。

### 防刷

活动级限流（单用户/单 IP 的 QPS 与请求总量）、下单前的图形或短信校验、黑名单。当前 `reserve` 靠 `SELECT ... FOR UPDATE` 统计限购，恶意请求会带着行锁排队，等于用数据库锁挡刷子。

### 什么条件下才值得上

单场瞬时并发超过几百，或出现因秒杀影响其他业务的投诉。日订单量和秒杀场次都在当前量级时，标准版的复杂度和收益不成比例。
